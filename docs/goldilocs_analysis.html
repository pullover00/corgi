Method analysis & redesign proposal

Render-and-Compare, Revisited

Our PASLCD pipeline descends directly from GOLDILOCS (Friedlander, Shamir & Fried, ICLR 2026) — hence the goldilocs conda env we've used all session. This document traces exactly where our implementation diverged from that design, backs each divergence with our own measured evidence, and proposes a point-cloud-native redesign informed by SceneDiff (arXiv 2512.16908), which already demonstrates 3D-centroid-based change output driving a real robot arm.

Based on: 41 completed PASLCD queries (18 scenes) · pixel-loss funnel analysis · 192-point threshold sweep · GOLDILOCS ICLR 2026 paper · SceneDiff arXiv 2512.16908v2
The two papers Architecture diff What helps / hurts Point-cloud redesign Roadmap

In one sentence: our pipeline added a mandatory 2D-appearance identity gate (SAM3+DINOv2 cosine similarity) on top of GOLDILOCS's original track-centric design, and that single addition is responsible for the majority of our measured failures on PASLCD — a dataset GOLDILOCS itself was never evaluated on.

The fix isn't just re-tuning that gate's thresholds (we tried — it recovers ~8% relative F1, not the 10-40x gap to GOLDILOCS's own reported numbers). It's replacing 2D appearance matching with the 3D geometric matching both source papers actually rely on for the hard cases — which also happens to be exactly the representation a robot arm needs.

Section 1

The two papers

One gave us our architecture; the other gives us the missing piece.

ICLR 2026

GOLDILOCS: General Object-Level Detection and Labeling of Changes in Scenes

Friedlander, Shamir, Fried — Reichman University
"SCD can be reformulated as a 3D reconstruction problem over time, where geometric inconsistencies naturally indicate change."
  • MASt3R stereo reconstruction → reverse-depth-conflict filtering → canonical clean pointmap P* (this is our reverse_depth_filter, verbatim)
  • Single segmentation/tracking model throughout: SAM2 proposes and tracks — no separate identity-feature model
  • Change decided purely by tracking success/failure against the clean render, then moved-vs-removed by a second track into the real photo — no mandatory appearance-similarity gate
  • Five classes: Added, Removed, Moved (full/partial), Warped (non-rigid, via SSIM) — we have four, and dropped Warped
  • Never evaluated on PASLCD — its benchmark suite is ChangeSim, VL-CMU-CD, RC-3D, NeRFCD, 3DGS-CD, 3RScan
  • Cross-view voting (multi-image T1) is its dominant precision mechanism — Table 11: without it, precision on 3DGS-CD scenes crashes to 59-80% at ~100% recall; with it, 95-98%
arXiv 2512.16908v2

SceneDiff: A Benchmark and Method for Multiview Object Change Detection

Wu et al. — also the source of the PASLCD-adjacent evaluation protocol and SAM region-generation pipeline we reproduced earlier this session
"A region is considered another view of an existing object if their features and 3D points are similar" — matched via feature cosine similarity and geometric point-cloud proximity, threshold σgeo=0.02.
  • Represents each candidate object as its own 3D point cloud (masked region lifted via depth), not just a 2D crop
  • Object identity across frames = joint 3D-proximity + appearance test, not appearance alone
  • "Directional visibility mask" (non-negative depth differences + FOV reasoning) separates real change from viewpoint occlusion — same spirit as GOLDILOCS's depth-conflict test, different derivation
  • Demonstrates a closed-loop robot-tidying application: computes the 3D centroid of each changed object as the grasp point, feeds it to inverse kinematics on a 7-DOF arm

Where our pipeline diverged from GOLDILOCS

Same backbone (3D reconstruction → depth-conflict cleaning → render-and-compare), different identity-matching core.

4 Track mask R0,1→R*,1: fails to track ⇒ candidate-changed

Section 4 — the proposal

Point-cloud-native identity matching

Keep render-and-compare. Replace the part that's actually failing: how we decide two proposals are "the same object."

Every object proposal we already produce sits on top of a rendered frame whose per-pixel 3D world points are already computed — ReconstructionResult.input_points / the reference scene's world_points array. Masking that array by a 2D proposal gives its 3D point cloud for free; no new reconstruction, no new model. We are one array-index away from SceneDiff's actual mechanism.

Why this specifically fixes our failure mode

  • Render/photo appearance gap, gone structurally. Our dominant failure (direct_identity) is a 2D-appearance mismatch between a synthetic render and a real photo — lighting, splat artifacts, JPEG compression all live in RGB space. Two point clouds of the same physical object agree in world-metric space regardless of how either frame was rendered.
  • Matches what both source papers actually do for the hard cases. GOLDILOCS's real decision variable is 3D-consistent tracking through the clean pointmap; SceneDiff explicitly requires 3D proximity (σgeo=0.02) alongside appearance, not appearance alone. Our appearance-only-or-track-only OR-gate is the outlier, not the norm.
  • No structural dependency on multiple query views. Centroid/point-set proximity is evaluated per-object against the single query photo we do have — it doesn't need GOLDILOCS's cross-view vote to get its precision, so it's a genuine alternative to the one mechanism PASLCD's protocol denies us (Section 3).
  • Directly produces what a robot needs. SceneDiff's own robot-tidying demo consumes exactly this: a changed object's 3D centroid as a grasp point, before/after centroids for a moved object. If identity is decided in 3D in the first place, the manipulation-ready output falls out for free instead of needing a separate 2D-to-3D lifting step afterward.

Sketch of the replacement test

def geometric_identity(source_points_3d, target_points_3d,
                        centroid_thr=0.05, overlap_thr=0.3):
    """Replaces the mandatory (sam >= 0.65) & (dino >= 0.60) gate.
    Both point sets already sit in the SAME world frame -- no render/photo
    appearance gap to bridge, unlike 2D cosine similarity on rendered RGB."""
    source_centroid = source_points_3d.mean(axis=0)
    target_centroid = target_points_3d.mean(axis=0)
    centroid_ok = np.linalg.norm(source_centroid - target_centroid) <= centroid_thr

    # cheap point-set overlap: fraction of source points within a target
    # KD-tree query, symmetrized -- a coarse Chamfer / IoU stand-in
    overlap = point_set_overlap(source_points_3d, target_points_3d)
    overlap_ok = overlap >= overlap_thr

    return centroid_ok and overlap_ok  # geometry decides; SAM3/DINOv2 scores rank ties only

This is additive, not a rewrite: keep identity/reciprocal/tracked exactly as implemented, add geometric alongside as a fourth signal, and change the gate from identity & (tracked | reciprocal) to geometric & (identity | tracked | reciprocal) — demoting 2D appearance from mandatory to corroborating, matching how tracking already behaves today.

Section 5

Suggested order of work

Cheapest, best-evidenced fixes first; the point-cloud redesign is the one structural change, everything else is validation and closing gaps.

1

Validate the tuned thresholds on a full run

sam≥0.55 / dino≥0.40 / track≥0.50 / spatial≥0.30 beat defaults on all 48 sampled queries (F1 0.106 vs 0.100) but only replay the direct_identity path — confirm on a real end-to-end run before committing.

Low effort
2

Implement the geometric-identity test

Mask world_points by each proposal, add centroid+overlap as a fourth signal alongside identity/tracked/reciprocal, demote appearance to a tiebreak. Directly targets the 90%-of-loss direct_identity failure mode.

Medium effort
3

Fix _suppress_feature_matched_parts's geometry-only suppression

Require the new 3D-geometric test (not just 2D bounding-box adjacency) before a small object can be suppressed as a "part" of a larger one — the second-largest measured loss point.

Medium effort
4

Replace the removed border filter with GOLDILOCS's coverage-fraction filter

Their α-parameter discards masks mostly supported by occluded/out-of-view pixels, using actual reconstruction coverage rather than "touches the frame edge." We already compute render_t0_coverage_fraction — just not for this purpose yet.

Low effort
5

Port SSIM-based Warped detection

Closes a real capability gap on any PASLCD object that deformed without moving. Needs an SSIM heatmap over each static mask, standard-deviation threshold — no new model.

Low effort
6

Design a PASLCD-specific precision safeguard

Cross-view voting needs multiple T1 views we don't have. Investigate an analogue using the reference side's redundancy instead: does a candidate change hold up when checked against several of the 24 reference views independently, not just the one used for rendering?

Open research question
